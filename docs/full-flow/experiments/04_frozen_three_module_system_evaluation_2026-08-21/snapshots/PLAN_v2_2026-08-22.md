# 冻结三模块系统完整实验计划（v2）

**日期：** 2026-08-22  
**状态：** `DESIGN FROZEN / IMPLEMENTATION PENDING / NO HELD-OUT SCORED`  
**取代范围：** 本文件取代 2026-08-21 版本的“三系统版本”设计；旧版已保存在 `snapshots/PLAN_v1_2026-08-21.md`。

## 1. 本次实验要回答什么

这次最终实验只回答三个问题。

1. 冻结后的完整系统 `Ours` 是否优于两个同 backbone 的 RAG baseline？
2. `Retriever`、`Selector`、`Generator` 三个模块各自对完整系统贡献多少？
3. 如果系统没有提升，问题发生在检索覆盖、证据筛选、答案正确性、引用质量，还是最终可靠答案率？

HotpotQA、MuSiQue 和 RGB 必须分别报告。不能把三个数据集平均成一个总分后掩盖某个数据集上的退化。

## 2. 冻结方法

### 2.1 Ours

`Ours` 是唯一的最终方法：

```text
Hybrid RRF Retriever
  -> NLI harm/protect Selector
  -> grounded Granite GR-C Generator + TRUE verifier
  -> MiniCheck external citation scoring
```

- Retriever：StrongBM25 与 Granite dense embedding 用 RRF 融合，`k=60`，输出 Top10。
- Selector：冻结的 NLI harm/protect selector，seed 13，checkpoint `86622bd9...72bf`，threshold `0.9212157130241394`，最多删除 2 条，至少保留 7 条，异常时全部保留。
- Generator：冻结的 Granite 4.1-3B grounded GR-C generator，seeds 13、42、73 全部报告，不挑最好 seed；greedy decoding，最多 256 个新 token。
- Verifier/scorer：TRUE 是运行时 verifier；最终引用质量由 MiniCheck 独立评分。

### 2.2 主比较 baseline

主实验只放两个 baseline，避免表格臃肿。

| System | Retriever | Selector / Pruner | Generator |
|---|---|---|---|
| Vanilla Granite RAG | Granite dense | Top10 keep-all | Direct base Granite |
| Granite + Provence | Granite dense | official Provence, threshold 0.1 | Direct base Granite |
| Ours | Hybrid RRF | NLI harm/protect | Grounded Granite GR-C + TRUE |

这张主表只能支持“完整系统比较”。因为 `Ours` 同时换了 retriever、selector 和 generator，模块归因必须看消融表，不能从主表直接声称某一个模块单独带来全部提升。

## 3. 数据集

主实验只使用三套 held-out 数据。它们不是这次临时构思，也不是报告模板硬性指定；它们是项目在 7 月底至 8 月中预留、且尚未正式评分的系统级测试集。

| Dataset | n | Role |
|---|---:|---|
| HotpotQA | 400 | 多跳问答和引用 |
| MuSiQue answerable | 400 | 复杂多跳问答 |
| RGB noise | 300 | 较大噪声候选池下的全过程表现 |

MuSiQue unanswerable 和 RGB counterfactual 不进入本次核心实验，也不设置单独的鲁棒性主表。NQ 已参与 Retriever 开发，因此不再作为最终系统测试集。

冻结的 ordered IDs 和原有 sample manifest 保持不变；MuSiQue 只读取每个配对 ID 的 `#ans` 版本。

## 4. 必做实验

### 4.1 主系统比较

对每个数据集运行三套完整系统：

1. `Vanilla Granite RAG`
2. `Granite + Provence`
3. `Ours`

`Ours` 报告三个 generator seed 的均值和标准差。两个 baseline 使用固定配置和 greedy decoding，报告一次确定性结果。

### 4.2 组件消融

消融从 `Ours` 出发，只改一个模块。为控制成本，消融使用 canonical generator seed 13；`Full` 行直接复用 `Ours` 的 seed-13 结果。

| Configuration | Change from Full | What it tests | Expected if useful | Priority |
|---|---|---|---|---|
| Full | none | 完整方法 | reference | MUST |
| w/ Dense Retriever | Hybrid RRF -> Granite dense | Hybrid retrieval 的净作用 | MuSiQue/RGB 的 Ret. 或 RAR 下降 | MUST |
| w/ Top-10 | NLI selector -> Top10 keep-all | Selector 的净作用 | Sel. 或 RAR 下降 | MUST |
| w/ Direct Generator | Grounded GR-C + TRUE -> direct base Granite | Grounded generator 的净作用 | Ans.、Cit. 或 RAR 下降 | MUST |

这些消融都不是 no-op。需要注意的是，HotpotQA 每题原本只有 10 个候选段落，`Ret.` 可能天然饱和；因此 HotpotQA 上的 `Dense Retriever` 更接近排序和上下文位置检查，不能单独用来声称开放语料检索提升。

## 5. 指标和表格写法

正式表格只使用短代号作为列名。

| Code | Meaning |
|---|---|
| Ret. | 全部官方支持证据中，进入检索 Top10 的比例，逐题计算后取宏平均 |
| Sel. | 同一批官方支持证据中，最终仍留在 Generator 输入里的比例，逐题计算后取宏平均 |
| Ans. | HotpotQA/MuSiQue 使用官方 token F1；RGB 使用 accuracy |
| Cit. | 逐题 MiniCheck citation F1 后取宏平均；空答案或非法引用记 0 |
| RAR | normalized gold-alias exact match 通过，引用索引合法，且 MiniCheck precision = recall = 1 的题目比例 |

`Ret.` 和 `Sel.` 使用完全相同的分母，因此 keep-all 系统自然有 `Sel. = Ret.`，检索阶段漏掉的证据不会被 Selector 指标隐藏。Provence 若在文档内部裁剪句子，按最小可用官方 support unit 是否仍存活评分，而不是只看文档 ID。所有值均按百分比展示，越高越好。

主文只放两张表：

1. Table 1：三个完整系统在三个数据集上的比较。
2. Table 2：三个组件消融在三个数据集上的比较。

每张表按数据集分成 `(a) HotpotQA`、`(b) MuSiQue`、`(c) RGB` 三个小面板。详细指标解释只放在表注里，不放进列名。

## 6. 公平性规则

1. 同一数据集的所有系统使用完全相同的 query IDs 和原始候选池。
2. Retriever、Selector、Generator 运行时不能读取 gold answer 或 support labels。
3. Gold labels 只在生成完成后的 scorer sidecar 中使用。
4. `Provence` threshold 固定为 0.1，不在 held-out 上调参。
5. 所有系统使用同一输出长度、同一 citation 格式要求和同一外部评分脚本。
6. Table 1 只做完整系统比较；Table 2 才做模块归因。
7. 如果某个系统 runtime error rate 超过 1%，该数据集先判为技术无效，不从剩余样本凑结果。
8. Held-out 结果出来后，不允许改阈值、换 seed、换样本或重新定义主指标。

当前统一 loader 出于运行时隔离而没有保留 support labels。正式运行前必须增加 scorer-only sidecar：HotpotQA supporting sentences、MuSiQue supporting paragraphs、RGB positive documents；它只在生成完成后评分，runtime pipeline 不可访问。

Provence 尚未在仓库中接通，但实验身份已经冻结为 `naver/provence-reranker-debertav3-v1@ef49e233e3c6e50efc476c68f1390f8a63add4d4`、threshold `0.1`、`always_select_title=True`、`reorder=False`。实现时必须记录权重 hash，并保留裁剪片段到原 source 的映射；不得根据 held-out 结果调整。

- Generator recipe、learning rate、LoRA rank 或 prompt 网格；
- 完整 `2 x 2 x 2` 三模块全因子网格；

这些实验要么已经由旧开发实验覆盖，要么工程成本高但不能直接回答本次主问题。

## 8. 运行顺序

1. Preflight：核对 held-out manifest、模型 hash、Provence 配置、scorer 配置和输出目录。
2. Smoke check：只用 synthetic 或已揭示 development 样本，确认三个主系统和三个消融都能产出 trace、generation 和 score。
3. 主系统正式运行：跑 `Vanilla Granite RAG`、`Granite + Provence`、`Ours` 三个 seed。
4. 消融正式运行：跑 `w/ Dense Retriever`、`w/ Top-10`、`w/ Direct Generator`，其中 `Full` 复用 `Ours` seed 13。
5. 统一评分：answer、MiniCheck citation、RAR 和 runtime 全部由同一 scorer 生成。
6. 表格落盘：生成 CSV、JSON 和 Markdown 渲染；论文表格只从 CSV/JSON 读取数值。

每个数据集的所有比较系统必须放在同一个 job/bundle 内，不能把同一数据集的系统拆到两张 GPU 后跨 job 拼结果。调度方式固定为：GPU 0 跑完整 MuSiQue bundle；GPU 1 跑完整 HotpotQA bundle，完成后再跑完整 RGB bundle。

## 9. 统计报告

- Table 1 中，`Ours` 的 `Ans./Cit./RAR` 报告 seeds 13/42/73 的 mean ± sample SD；固定的 `Ret./Sel.` 只报一个数，不写虚假的 `± 0`。
- 两个确定性 baseline 各运行一次，只报一个数。
- Table 2 全部使用 canonical seed 13，只报一个数；`Full` 直接复用 Table 1 的 seed-13 结果。
- 主比较对 `RAR` 做 query-paired bootstrap 10,000 次：先在每题内平均 Ours 三 seed，再与 baseline 配对。
- 消融用 `Full` seed 13 与对应变体做同样的 paired bootstrap。
- `ΔRAR` 与 95% CI 放在正文或表注，不增加表格列；不做 seed t-test，不把 n=3 的 SD 写成显著性证明。

### 9.1 结果怎样解释

- `RAR` 是主判断；`Ret./Sel./Ans./Cit.` 用来解释变化发生在哪一步。
- 某数据集的 `ΔRAR` 95% CI 下界大于 0：可以写“该数据集上有统计可信提升”。
- point estimate 为正但 CI 跨 0：只能写“有正向信号，但证据尚不确定”。
- 某项消融没有降低 `RAR`：不能声称该模块已带来端到端收益，即使它以前有模块内部正向结果。
- 三套数据分别下结论，不制造一个总平均来掩盖退化。

## 11. 工期估计

主数据共有 1,100 条：HotpotQA 400、MuSiQue answerable 400、RGB 300。

不考虑复用时，预计生成次数约为：

- Vanilla Granite RAG：1,100 次；
- Granite + Provence：1,100 次；
- Ours：1,100 x 3 seeds = 3,300 次；
- w/ Dense Retriever：1,100 次；
- w/ Top-10：1,100 次；
- w/ Direct Generator：1,100 次。

总计 **8,800 次新的答案输出**。`Full` seed 13 已从主实验复用，不需要第九个输出；字节级输入完全一致时可以使用带记录的缓存，但工期不依赖缓存节省。

历史同类 Granite 任务的生成速度约为 6.18--19.91 秒/条。折算后：

- 现实纯生成：约 21--27 GPU 小时；
- 加上 Provence、MiniCheck、retrieval、selector、I/O 和汇总：约 26--34 GPU 小时；
- Provence 接线和六配置 smoke check：顺利时约 2--4 小时，项目排期预留半天；
- Provence 已接通且两张 A4000 可独占时，正式实验现实墙钟约 20--28 小时；
- 为长上下文、模型切换和一次完整 bundle 重试，正式实验保守预留 36--48 小时；
- 从开始补齐接线到两张报告表落盘，建议按 **2--3 个自然日** 排期。

以上按 2026-08-21 最后一次记录的两张空闲 RTX A4000 估算。2026-08-22 当前无法重新连接服务器确认实时占用，因此启动前必须再检查一次；如果只有一张卡可用，正式墙钟应接近翻倍。
