## 4. 这个项目特有的失败模式 —— 这一节最重要

> **最危险的 bug 不是崩溃,是产出看起来合理的数字。**

这不是一句格言,是被反复实测出来的。**光 2026-08-08 一天就撞了两次:**

- `sacct -X -S <date>` 返回十行、格式完整、无报错,**静默漏掉了四条**。
  若不是按 job id 直查,唯一自然的读法是"台账的作业号写错了"——一个错误的结论,
  由一份看不出残缺的输出支撑。
- `decontaminate` 按**原始字符串**比对页面,而下游每个泄漏检查按 `normalize_parent`
  (casefold + 折叠空白)比对。同一个维基页的两种拼法在导出器眼里是两个页、一个都不删。
  它没报错,只是少删了东西。

历史上同类的还有:三类折叠成二分类时求和而非取 max(求和等价于引入一个被禁的阈值);
MiniCheck 的 label token id 按文本查表(不报错,只是给两个无关词表项做 softmax);
`sys.getsizeof` 估出来的内存数(与真语料 peak RSS 矛盾,已作废)。

**由此得到的三条工作方式,请照做:**

1. **凡是写成"必须先做 X"的纪律,要么让代码强制产出 X,要么它迟早被跳过。**
   已经有多处按这条改成机制:检索器冻结、sealed-600 的候选池 pin、
   §3.8 把 `--epochs` / `--learning-rate` / `--batch-size` 从命令行**直接删除**
   (协议既写明无合法调参面,留着参数只能用来漂移)。
2. **改完之后要有可证伪的读数,不能只看命令报不报错。**
   2026-08-08 修完 `decontaminate` 重导出,`n_train` 一个数没变 —— 因为 bp1 是另一个 checkout,
   改动还在本地没提交,**跑的是旧代码**。当时预测是写死的,所以"和之前一样"立刻被识别成异常;
   若没写,它会被读成"没影响,继续",然后在同一个守卫上再挂一次。
3. **守卫失败是好事。** R013 至今五次 FAIL,五次都在拿到卡之后、加载模型之前秒级失败,
   **烧掉的 GPU 时间是 0**,而其中一次拦出的是真实数据缺陷。
   如果没有那个守卫,训练会正常跑完、产出一个模型、per-class F1 看着完全正常——
   而它训过一条本该只属于校准面的页。
