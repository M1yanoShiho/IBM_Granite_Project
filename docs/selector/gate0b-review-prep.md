## Q1. 指标为什么在门失败之后才改?这不是移动球门吗?

**先承认时序,不要辩解时序。** 修订确实是在看到 FAIL 之后提出的,这一点写在 `M0_PROTOCOL_FREEZE.md` §9.0,
包含逐日时间线,并声明"本文件的作者无法主张未受结果影响"。

**然后给三条可独立核验的事实**(§9.0 后半):

1. **依据早于数据。** "主口径下 REFUTES 边只被记录不被门消费"写在 commit `10a1314`(2026-07-30),
   彼时 Gate 0B 一个数字都不存在。`git show 10a1314` 可自行核验,不必采信我们的自述。
2. **修订没有制造任何通过者。** argmax 口径下四种(臂 × rung)组合仍全部未过 `gold_supports_recall`
   (最高 .7942 < .85)。修订只把 FAIL 的原因从两项收敛到一项。可证伪:重跑 dump 即可检验。
3. **修订把推翻自己的权力交给了尚未产生的数据。** §9.8 指定 MiniCheck-FT5 与 rung 3 为出样检验,
   明文规定"若出样结果与本修订预期相悖,以出样结果为准"。

**关键句:** 我们没有把 FAIL 改成 PASS,门至今没过。

## Q2. 你怎么保证这不是 p-hacking?

**最强的证据是我们主动关掉了一扇能通过的门。** 2026-08-03 的阈值扫描显示,
DeBERTa / rung 1 在 `P(SUPPORTS) > .05` 时 gold-recall **.9015**、twin **.7374**,**两项同时过**。

**我们拒绝采用它**,并把拒绝的理由写成协议条款(§9.5a),三条:

- 采用它会使 §9.5"四种组合仍无一通过"当场变假,A1 自证不放水的唯一直接证据随之作废;
- θ 是直接对着 Gate 结果调出的自由参数,除"它能过"外无任何独立依据;
- **实质理由:** θ=.05 意为"有 5% 概率即判支持",在真实 20 段池中会产生大量假支持边,
  而该失败恰由 §3.5 G-FC 护栏承接;§3.3 的 S6 纪律写死 0B-2 是隔离对探针、不许外推到池。
  **在隔离探针上调阈值调到过关,不构成系统可工作的任何证据。**

**再加一条来自代码的:** `relations/predictor.py` 的 docstring(早于本轮)写明阈值补救是预注册的,
但触发条件是 **REFUTES precision 不足**;实测 albert .9026 / DeBERTa .9127,**两臂均过 .85,触发条件未满足**。
以 recall 不足为由引入阈值不在该预注册补救范围内。

## Q3. 如果第三类没用,"关系图"还剩什么?这不是降级吗?

**如实回答:主口径本来就只用 SUPPORTS。** `independent_support(K)` 的定义只数 SUPPORTS 边,
`conflict_mode=distinct_cluster`(主口径)用簇成员关系而非 REFUTES 边。
**修订暴露了这一点,不是造成了这一点。**

**代价要主动列出**(§9.7):`conflict_mode=refutes_edge` 消融臂失效、TRAINING_PLAN Block 3 的
"去掉 CLAIM_REFUTES"消融失去含义、tracker 的 R036 整行变空。

**不要辩称没有损失。** 正确的说法是:这是一个关于设计的发现——我们为一个机制从未消费的量设了验收门,
并因此把两个模型判成不合格。**这比"我们的图有三种边"更值得写。**

## Q4. 这是 IBM Granite 项目,为什么关系层用了两个非 IBM 的小模型?

**技术回答(有实测支撑):**

- IBM 在 HF 上**没有 NLI cross-encoder**。Granite 系列是 embedding(双塔检索)、speech、生成式 LLM。
- 唯一的 IBM cross-encoder 是 `granite-embedding-reranker-english-r2`(149M,ModernBERT,8192 上下文,
  Apache 2.0),但它输出**相关性分数**,用 pListMLE 排序损失训练,**没有 entailment / contradiction 概念**。
  **零训练直接用会失败在最坏的方向**:反驳某 claim 的段落对该 claim 高度相关,相关性 reranker 会给
  反事实孪生打高分——恰是我们要抓的失败模式,却被写进了它的目标函数。
- **Granite 做判官已被本项目实测过**(`docs/generator/verifier-triage-results-hpc.md`):
  `granite-4.1-8b` ASQA entail recall **.900** 但 precision proxy 仅 **.484**(hard-neutral 24% 误判为支持);
  `granite-4.1-3b` .767 / .742。**高召回低精度,对一个"别放毒进来"的门不可用。**

**必须同时承认的流程缺陷:** 这个理由**当时没有写在任何地方**。两个 checkpoint 随设计文档
(`10a1314`)静默进入,关系层设计全文未讨论 Granite,且与 G 模块那轮六臂 triage **互不引用**。
这是决策记录缺失,已补记。

**正面方向:** `granite-embedding-reranker-english-r2` 是 §3.8 微调底座的最佳候选——149M(albert 独立参数
仅 59M)、8192 上下文(albert/DeBERTa 为 512)、已是 cross-encoder、Apache 2.0,**且让关系层回到 Granite 家族**。
风险如实说:它没有 NLI 先验,contradiction 要从零学。

## Q5. 预注册了三臂,为什么只跑了两臂?

**缺的是 MiniCheck-FT5(770M,LLM-AggreFact <1B SOTA)**,即三臂中**唯一为 document-grounded verification
专训**的一臂,也是本项目自己实测最优的验证器(2Wiki atomic **.917**,distractor→entail 仅 .017)。

**两个原因叠加:** slurm 的 `MODELS` 是死变量(已修);更根本的是它是二分类、需否定 claim 双向探测,
而 `load_score_fn` 只有三类 argmax 路径——**即使接了线也上不了场**。

**因此必须主动限制结论范围:** 本轮**不支撑"任何零训练模型都不够"的族级断言**,
只支撑"这两类通用/域内 NLI checkpoint 在当前口径下不够"。该限制已写进 R012 AFTER 与 tracker。
**若被问到"你怎么知道不是模型选错了"——正确答案是"我们还不知道,这一臂没跑"。**

## Q6. albert 在 VitaminC 上 .92、在你的探针上 .19,会不会是探针有问题?

**这是好问题,而且我们把它当主假设查了。六个候选机制全部由实验排除:**

| 机制 | 实测 |
|---|---|
| 截断 | `frac_over_cap` 两臂均 **0.000**(premise 中位 150 token / cap 512) |
| 标签序错配 | 同一映射下 0B-1 macro-F1 .922 |
| 答案规范化改坏 claim | answer 串 **97.6%** 逐字出现在 premise 中(干净对照组 100%) |
| 大小写 | albert `do_lower_case=True`,对塌陷臂**可证无影响** |
| premise 文本质量(CSV 转义残留) | 带残留 .369(n=899)vs 干净 .354(n=573),**< 1 SE** |
| premise 长度 | 长 .362 vs 短 .365,**< 1 SE** |

**而两个确实是探针的问题,我们自己找出来并量化了:** hypothesis 句式(albert twin .674 → **.760**)
与三类 argmax 记账(gold-recall .1916 → **.7018**,3.66×)。

**还有一个诚实项:** rung 3(QA2D)未跑,是最后一个未测的测量变量,**结论到此为止,不再外推**。

## Q7. 你说句式是原因,会不会只是换到了一个"更容易"的形式?

**反向证据是最有力的:同一改动让 DeBERTa 两项各退 12.9pp / 8.3pp。**
若 `{q}? {a}.` 单纯更容易,两臂应同向改善。

**机制解释(已写进台账,含对自己设计的更正):** rung 2 去掉了元指称框架,**但同时不再是陈述句**。
albert(VitaminC 短 claim 调出)吃前者的红利,DeBERTa(MNLI/ANLI 规范陈述句)吃后者的亏。
**我们原本声称"每级只移除一个变量",这是错的,已在 R012b AFTER 中更正。**
rung 3 是唯一"−元指称 +合语法"的那一格,因此更重要。

## Q8. 门没过,这个项目还剩什么?

**门的成败不是唯一产出。** 可独立成立的结论(S7):

> 零训练验证器的评估结论,对 **hypothesis 的句法形式**与**标签空间的记账口径**的敏感度,
> **高于对模型选择的敏感度**。一个在官方 test 上 macro-F1 .922 的 checkpoint,
> 可以在任务形状的探针上被测成 .19,而其中大部分是测量方式。

**附带的可复用方法:** 仅由 aggregate 比率即可对未被任何指标统计的类别导出弃权率**下界**
(R012 AFTER 推得 cf_replacement 弃权 ≥46.8%,实测 64.0%)——**不重跑模型就排除一整片假设**。

**以及一条尚待验证但有分量的:** S4 记录的"三轮抽取层工作没能修好"的孪生判别,
一个 59M 现成 checkpoint 在换掉 hypothesis 句式后达到 **.760**。

## Q9. R011b(探针构造)没有台账条目,你怎么保证探针是对的?

**不回避:这一步确实是用一条与文档不符、且未入台账的命令建的。** 所有文档都写 `runs/niah-train/`,
而**该路径产不出任何一对**——探针需要反事实文档与 mutation log,两者只在注入后存在。真实路径是
`runs/niah-train-injected/`。**R011b 是 M1 里唯一没有台账条目的一步,这个缺陷因此无人发现。**

**能给出的保证:** 2026-08-03 用真实路径重导得 `n_pairs 5888 / n_records 1472 / n_skipped_records 0`,
与 job 18235972 消费的探针**分母逐字吻合**,故实验有效性不受影响。**这是记录纪律问题,不是数据问题。**
tracker 中 R011b 状态**保持 TODO 而非 DONE**——按本项目规则,没有台账条目的运行不算已记录。
